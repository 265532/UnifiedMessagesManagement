命名规则：

1. 00～06 主文件严格保留官方序号、下划线和中文名；扩展名统一小写。
2. 中间源稿使用“两位序号 + 英文小写短横线”命名，避免多个 Agent 覆盖同一文件。

7. 所有缺失事实统一写 `待补充/待确认`，不得以虚构数据填空；内部草稿中的占位必须在最终交付前清零或由人工书面确认保留原因。

## 4. Word/Excel 通用验收规范

除各任务专项要求外，`01`～`05` 及独立可行性 Word 文档统一执行：

- 首页：项目名称（宋体、加粗、三号、居中）、文档名称（宋体、加粗、四号、居中）、队伍人员与报名序号（宋体、四号、居中）。队伍人员和报名序号当前为 **待补充/待确认**。
- 第二页：以 Word 引用/自动目录方式生成目录；小四、仅显示至二级标题、1.5 倍行距。
- 第三页起正文；正文页码从 1 开始。标题采用 `1.`、`1.1`、`（1）` 层级，最多三级。
- 一级标题宋体小四加粗；二级标题宋体五号加粗；三级标题及正文宋体五号；标题和正文均 1.5 倍行距。
- 表格有边框、表序号和表名；图居中并有图序号、图名和简要说明。图说明不超过 300 字。
- 若使用 AI，按要求在相应文档“其他”中附专项 AI 对话过程链接。链接当前 **待补充/待确认**；须确认可访问且不泄露隐私或密钥。
- `00_提交清单.xlsx`：字段为“序号、提交文档名、内容简介”；标题居中，序号和文档名列居中，内容简介正文两端对齐；所有已填写单元格（含标题）及表格方框有边框。
- 最终由 QA-Agent 在 Word/Excel 中实测版式，不仅检查 Markdown 源稿。页数、目录、页码、图表、字体与对齐均保存检查记录。

## 6. 整体执行顺序与并行编组

### 6.1 推荐顺序

```text
Wave 0（立即，P0）
  SUB-00 提交信息与人工阻塞确认
  └─ 并行推进 PREP-01/PREP-02；PREP-03 需人工与真实测试企业

Wave 1（设计基线，按 Harness 依赖）
  RA-01→RA-02→RA-03→RA-04（SUB-01 可先整理草稿）
  DS-01→DS-02
  DS-02 后并行：DS-03 / DS-04 / DS-05
  DS-05 后：DS-06

Wave 2（资料与实现并行，但不能伪造状态）
  SUB-01 需求分析
  SUB-02 原型素材与文档（DS-05/DS-06 就绪后定稿）
  SUB-03 数据库设计（DS-04 就绪后）
  SUB-04 接口设计（DS-05 就绪后；与 SUB-03 交叉核对）
  产品 IM/QA 按 feature_list 依赖推进，为 SUB-05/SUB-07 提供真实输入

Wave 3（验证与汇总）
  SUB-05 初步验证（关键路径实现后）
  SUB-06 可行性/精简设计（设计与验证输入就绪后）
  SUB-07 仓库与运行说明（可运行初版后）

Wave 4（串行收口）
  SUB-08 → SUB-09 → SUB-10 → 人工官方提交
```

### 6.2 关键依赖关系

1. **报名/赛题确认（PREP-01）** 是需求基线正式通过的前置；不能用已有赛题文档替代人工确认。
2. **DS-01 技术选型** 阻塞真实技术描述及后续实现；候选栈不得写成最终采用。
3. **DS-02 统一消息 Schema** 是状态机、数据库、接口的共同上游。
4. **DS-04 → SUB-03**，**DS-05/DS-06 → SUB-02/SUB-04**；接口涉及数据表需与 SUB-03 交叉核对。
5. **真实实现与 QA 证据 → SUB-05/SUB-07**；这是当前最大关键路径，文档 Agent 不得代造。
6. **SUB-01～07 源稿齐套 → SUB-08 → SUB-09 → SUB-10**；最终清单和验收不得提前并行定稿。
7. 初赛范围为 Must 闭环；企业微信第三平台、AI 摘要、高可用等 Could 项不得阻塞提交。若采用 AI 编写文档，仍须按官方要求提供专项对话链接。
8. 所有 Harness `passes` 只能经 `verify` 更新；上游回退后下游需重新验证。

## 9. Sub agent 分派执行约束

1. 每个 Agent 开工前读取 `AGENTS.md`、对应 `.harness/roles/<role>.md`、本任务段和必要输入；一次只领取一个主任务。
2. Super-Agent 分派时提供：任务 ID、目标、输入文件、允许写路径、前置依赖、验收标准和验证命令；不要把全部历史对话塞给子 Agent。
3. 各 Agent 只写角色允许路径；发现产品缺陷由对应 Dev 修复，QA 不改产品代码制造“假绿”。
4. 交付报告必须列出实际产物、命令、退出码、证据路径、未解决问题；“已生成文件”不等于“任务通过”。
5. 同一任务最多自动重试 2 次；重复错误或无新证据即停止并升级，不反复重写同一文档。
6. 未经人工明确批准，不执行远程 push/发布、不向真实用户发消息、不申请真实权限、不删除/重置数据。
7. 最终提交前逐项清除未授权的占位和待确认标记；若仍缺关键证据，应在交接中明确“不可提交/有条件提交”，不得隐瞒。

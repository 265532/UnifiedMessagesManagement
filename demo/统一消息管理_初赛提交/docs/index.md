## 三个里程碑

| 编号 | 日期 | 内容 | 怎么判定通过 |
|---|---|---|---|
| M1 | 11/13 | 飞书单平台闭环 | 飞书来的消息能在网页看到，网页回复能在飞书里收到 |
| M2 | 11/15 – 11/17 | 双平台收发互通 | 两个平台的回复都能真发出；钉钉接收改用 Stream 长连接，11/17 手机端实测打通，不需要公网。飞书接收仍卡在公网 https 回调 |
| M3 | 11/18 | 状态回流 | 网页回复后，平台侧状态变化能在网页上查到 |

M1 是整条链路上最早的风险点。飞书账号审批、回调地址配置、签名校验任何一环卡住，后面全部顺延。所以账号和第一次真实收发必须放在准备阶段解决，不能等到写代码时再试。

## 依赖关系

```
Schema / API 契约冻结
    ├── 飞书 Adapter ── 钉钉 Adapter ─┐
    ├── 前端（可并行开发）───────────┼── 状态回流 ── 测试 ── 初赛提交
    └── 脚手架 ── 核心服务 ──────────┘
```

契约没冻结就并行，返工成本远高于等两三天。这条是硬约束，不是建议。

## 风险与预案

| 风险 | 后果 | 应对 |
|---|---|---|
| 平台账号审批慢 | 连接器无法开工 | 准备阶段即提交申请；先跑通飞书，钉钉并行推进；RPA 只作最后兜底 |
| 接口 429 限流 | 发送失败，闭环中断 | 指数退避重试 + 发送队列削峰 + 限流阈值监控 |
| Access Token 过期 | 接口批量失败 | 统一令牌管理，剩余有效期不足 300 秒主动刷新，失效后自动重发 |
| Webhook 重复回调 | 产生重复消息 | 平台事件 ID 作幂等键，Redis 去重 |
| 消息解析失败 | 异常消息无处理通道 | 进入 parse_failed 队列，人工复核后入库或归档 |
| 里程碑延期超过 1 天 | 初赛交付受影响 | 砍 Could 级需求，保 Must 闭环，加分项直接放弃 |

# 飞书接入：从建应用到跑通第一个闭环

目标很具体：把本项目从模拟模式切到真实飞书。在群里 @ 机器人说一句话，网页上能看见；从网页回一句，飞书群里真的收到。

全程大概需要 40 分钟，其中一半时间花在等审批。

## 0. 先确认三件事

- 有一个飞书账号。个人注册会自动建一个团队，但没做过企业认证的团队有可能调不了开放平台 API，先看第 9 节「关于 21001」再动手。
- 项目在本机能跑起来（`python app.py`，能看到 8000 端口）。
- 有一个**公网可访问的 https 地址**。飞书不收 http，也不能是 127.0.0.1。这一条最容易低估，见第 5 节。

## 1. 创建自建应用

浏览器打开 https://open.feishu.cn/app ，点「创建企业自建应用」。

名称填 `UnifiedMessages` 之类，图标随便选，描述可以留空。创建完会直接进应用详情页。

左侧菜单「凭证与基础信息」里有两个值，现在记下来：

- **App ID**：`cli_` 开头
- **App Secret**：一串字母数字，看不到全貌就点「重置」拿新的

App Secret 等同于这个应用的最高权限，别贴进聊天记录、别提交到仓库。

## 2. 开权限

「开发配置 → 权限管理」，用搜索框加这两个：

| 权限标识 | 用途 | 不开会怎样 |
|---|---|---|
| `im:message` | 接收群消息、单聊消息事件 | 回调能通，但事件收不到 |
| `im:message:send_as_bot` | 以机器人身份发消息 | 能收不能回，闭环断在发送那一步 |

想读群名称可以再加 `im:chat:readonly`，本项目当前没用到，可以先不加。

## 3. 添加机器人能力

「添加应用能力」→ 找到「机器人」→ 添加。

没有这一步，应用在飞书里没有身份，也就不会有群能拉它进去。

## 4. 配置事件订阅

「事件与回调 → 事件配置」，填四项：

| 项 | 填什么 |
|---|---|
| 请求地址 | `https://你的域名/webhook/feishu` |
| Verification Token | 复制出来，一会儿填到 `FEISHU_VERIFICATION_TOKEN` |
| Encrypt Key | **留空** |
| 订阅事件 | 搜索并添加 `接收消息 im.message.receive_v1` |

Encrypt Key 必须留空。填了之后飞书会用 AES 加密整个推送体，本项目没实现解密，收到的东西是一串密文，只会落成 `parse_failed`。

点保存时飞书会立刻往这个地址发一个校验请求：

```json
{"type": "url_verification", "challenge": "xxxxx", "token": "..."}
```

服务必须原样把 `challenge` 返回，才算保存成功。代码里已经处理了这一段（`app.py` 的 `webhook` 函数第一段）。如果这里提示「请求地址校验失败」，问题一定在地址不通或服务没起，不是应用配置。

## 5. 把本地服务暴露到公网

这一步决定你能不能在自己的电脑上调试。三个方案，按推荐程度排：

**方案 A：云服务器部署（最稳，推荐）**

买台最低配的云主机，把项目扔上去，用 Docker 或直接 `python app.py`，前面挂 nginx 配 https。这是决赛要求的独立部署形态，迟早要做，不如现在做。

**方案 B：内网穿透（调试期够用）**

cpolar、natapp、frp 任选。以 cpolar 为例：

```bash
cpolar http 8000
```

会给一个 `https://xxx.cpolar.top` 的地址，填到飞书回调地址就是 `https://xxx.cpolar.top/webhook/feishu`。

免费版地址每 24 小时变一次，一变就要回飞书后台改地址并重新校验，麻烦但能用。

**方案 C：路由器端口映射**

需要家里有公网 IP（多数宽带没有，是 NAT 后的内网），还得自己配 https 证书。不建议折腾。

## 6. 填凭证并重启

Windows 命令行：

```bash
set UMM_MODE=real
set FEISHU_APP_ID=cli_xxxxxxxx
set FEISHU_APP_SECRET=xxxxxxxx
set FEISHU_VERIFICATION_TOKEN=xxxxxxxx
python app.py
```

或者在项目根目录复制 `.env.example` 为 `.env` 填好，用 docker compose 启动时自动读。

改完必须重启进程。`config.py` 只在启动时读一次环境变量，热改无效。

## 7. 发布应用（最容易漏的一步）

「版本管理与发布」→ 创建版本 → 填版本号（1.0.0）→ 申请发布。

你自己是团队管理员的话，直接在管理后台点通过。不是的话要等管理员批。

**权限改动和事件订阅改动，不发布新版本就不生效。** 这是接入过程中最常见的坑：配置全都对，就是收不到消息，八成是版本还在草稿状态。

改一次权限就要发一次版本，别嫌烦。

## 8. 验证闭环

1. 飞书里建一个群（或者用已有的），群设置 → 群机器人 → 添加 → 选你刚建的应用。
2. 群里 @机器人 说一句话，比如「测试一下」。
3. 打开本项目页面 http://127.0.0.1:8000 ，一两秒内应该出现这条消息，平台标着蓝色「飞书」。
4. 点进详情，底部写一句回复，点「发送回复」。
5. 回飞书群看，应该收到机器人的回复。
6. 回本项目页面，点「确认回执」，右上角状态变成已确认，右侧流水线九步全绿。

这六步能走完，初赛要的「平台收发验证截图」就有了。截图建议截三张：群里 @ 机器人的原消息、本项目页面收到消息、群里收到机器人回复。

## 9. 出问题怎么查

| 现象 | 最可能的原因 | 怎么确认 |
|---|---|---|
| 保存回调地址提示校验失败 | 地址不通、服务没起、不是 https | 浏览器直接访问 `https://你的域名/healthz`，能返回 json 说明通了 |
| 地址保存成功，但群里发消息没反应 | 事件没订阅、或版本没发布 | 开放平台「事件与回调」页面能看到推送记录和失败原因 |
| 消息收进来了，状态是「解析失败」 | Encrypt Key 填了、或事件结构变了 | 查 `data/umm.db` 的 traces 表，看 `parse_failed` 那条的说明 |
| 点发送报错「获取 token 失败」 | App ID / Secret 填错，或环境变量没生效 | 重启进程；Secret 填的是重置后那个 |
| 点发送报错权限相关 | `im:message:send_as_bot` 没开，或没发布版本 | 回权限页确认，然后发新版本 |
| 同一条消息在页面上出现两次 | 平台重复投递 | 本项目有幂等，正常情况会被丢弃；如果真重复了，查 event_id 是否为空 |
| 拿 token 返回 `21001` | 租户策略拒绝，不是密钥错 | 见下面「关于 21001」，先做密钥对照实验 |

服务端日志在 `server.out.log` 和 `server.err.log`，出错先看这两个。

## 关于 21001

`21001 Access denied due to platform policy` 不在飞书的通用错误码表里，看见它容易先怀疑密钥填错了。别急着重置密钥，先做一个对照实验：

拿正确的 Secret 和随便编一个 32 位 Secret，各调一次 `tenant_access_token/internal`。前者返回 21001、后者返回 `10014 app secret invalid`，就说明密钥本身没问题，是应用或租户被策略挡了。这种情况下改代码、重置密钥、重发版本都没用。

2026-11-15 在本机实测过一次，结论记在这里，省得重复走：

| 检查项 | 结果 |
|---|---|
| App ID / App Secret | 正确（错误密钥返回 10014） |
| 应用状态 | 已启用 |
| 权限 `im:message` | 已开通 |
| 版本 | 1.0.0、1.0.1 均已发布 |
| IP 白名单 | 未开启 |
| `tenant_access_token`、`app_access_token` | 都返回 21001 |

以上全都对还是被拒，剩下的解释只有一条：这个租户没有被开放自建应用调用 API 的许可。用个人账号自动建出来的团队常见这种情况。

两条出路：

- **做企业认证**。认证通过后，同一套配置大概率直接可用，不用改代码。
- **先用群机器人 Webhook 把发送方向跑通**。自定义机器人不需要 App ID、不需要权限审核，拿到 Webhook 地址 POST 一个 json 就能往群里发消息，演示「真实平台推送」够用。添加入口在飞书桌面客户端的「群设置 → 群机器人 → 添加机器人」，网页版没有这个入口，得装客户端。收消息方向仍然依赖自建应用加公网地址，这条路替不了。

## 群机器人 Webhook：不建应用也能把消息推进群

自建应用被 21001 挡住时，发送方向还有一条绕开应用权限的路：群自定义机器人。不需要 App ID，不需要审核，也不需要公网地址，拿到一个 Webhook 地址直接 POST json 就能往群里发消息。

**1. 准备一个群。**自己建的群就行，只有一个人也能用。

**2. 加机器人。**入口只在飞书桌面客户端的群里：群右上角「…」→ 设置 → 群机器人 → 添加机器人 → 列表第一项「自定义机器人（通过 webhook 将自定义服务的消息推送至飞书）」。填名字（这里用的「统一消息管理」），描述留默认，点「添加」。

网页版 feishu.cn 的群设置里没有这个按钮，只开浏览器是加不了的，得装客户端。

**3. 拿 Webhook 地址。**添加完成会直接显示，形如 `https://open.feishu.cn/open-apis/bot/v2/hook/<uuid>`，点右边「复制」。

安全设置三项（自定义关键词、IP 白名单、签名校验）默认都不勾，不配也能发；勾了就要同步改代码。对话框会提示「尚未完成安全设置」，选「暂不配置」即可。

**4. 写进 `.env`。**

```
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/<uuid>
```

**5. 重启服务。**`config.py` 只在启动时读一次 `.env`，改完不重启不生效。

### 代码里怎么走的

`config.py` 的 `FEISHU` 字典多了 `webhook_url`。`adapters/feishu.py` 的 `send()` 按这个顺序判断：

1. `webhook_url` 有值 → 走 `_send_by_webhook()`，直接 POST 到群机器人。这一步在 mock 模式下也照样真发，所以演示形态是「接收用模拟、发送是真的」。
2. 没有 Webhook 且 `MODE=mock` → 假装发送成功。
3. 都没有且 `MODE=real` → 应用身份拿 `tenant_access_token` 再调发送接口。

Webhook 只支持文本。文件消息会直接返回明确错误（要发文件得先以应用身份上传素材拿 `file_key`，那条路依赖自建应用）。

### 怎么验证通了

发一条出去，几秒内客户端能看到，接口同时返回成功。本机实测过两轮：

- 通道自测：直接调适配器发一条 → 群里出现「Webhook 通道连通测试」
- 端到端：把一条飞书消息从「已入库」推进到「已发送」→ 群里出现对应业务回复

### 这条路的边界

- 只能发，不能收。收消息仍要自建应用订阅事件 + 公网 https 回调地址。
- Webhook 地址等同于群里的发言权限，谁拿到都能往群里推消息。它只能放在 `.env`（已被 `.gitignore`、`.dockerignore` 排除），不要写进文档、README、截图或仓库。

## 10. 凭证放哪、哪些别提交

所有凭证都从环境变量读，代码在 `config.py` 的 `FEISHU` 字典里，没有任何硬编码。

`.gitignore` 已经排除了 `.env` 和 `data/`。提交前确认一下 `git status` 里没有这两项。

## 还没做的部分

写在前面，省得踩坑：

- **加密推送不支持**。就是上面说的 Encrypt Key 必须留空。
- **发送者名字拿不到**。飞书消息事件只给 `open_id`，不给姓名，页面上显示的是「飞书用户」。要显示真名得额外调通讯录接口，还要申请 `contact:user.base:readonly` 权限。
- **只处理文本消息**。图片、卡片、富文本会进 `parse_failed`，需要再补解析分支。
- **钉钉的对接单独写了一篇**：`docs/钉钉接入指南.md`。发送方向同样走群机器人 Webhook，已真实跑通；回调签名校验也已经补上（HMAC-SHA256 加时间戳防重放），但没有公网回调地址，只在单元测试里验证过。
- **飞书的真实收发只通了一半**。发送方向靠群机器人 Webhook（`FEISHU_WEBHOOK_URL`）已经能真推到群里；接收方向因为自建应用被 21001 挡着、本机又没有公网回调地址，页面里的飞书消息仍是 mock 造的。演示时要讲清楚这一点，别让评委以为消息是从真飞书群收上来的。

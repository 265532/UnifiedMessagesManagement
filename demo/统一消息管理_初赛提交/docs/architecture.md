# 架构与关键设计

这份文档只讲代码里真实存在的东西，以及当时为什么这么选。没实现的不写进来。

## 分层

```
浏览器（单页，原生 JS）
   │  REST + SSE
Flask 应用层（app.py）
   │  路由、登录、会话、参数校验
服务层（core/service.py）
   │  流程编排：接收、回复、重试、回执
   ├─ 状态机（core/state_machine.py）
   ├─ 标准格式（core/schema.py）
   ├─ 存储（core/store.py，SQLite）
   └─ 事件总线（core/bus.py，SSE）
适配器层（adapters/）
   │  飞书 / 钉钉 / 模拟事件源
平台开放 API
```

三层各管一件事：适配器只管跟平台说话，服务层只管业务顺序，应用层只管收请求和发响应。平台差异全部挡在适配器里。

## 为什么用适配器模式

要解决的问题很具体：飞书和钉钉的消息体、令牌机制、发送接口都不一样，如果核心代码里到处是 `if platform == "feishu"`，加第三个平台就得改几十处。

现在的做法是定义三个方法（`adapters/base.py`）：

| 方法 | 职责 |
|---|---|
| `verify(payload, headers)` | 判断这次回调是不是平台真发来的 |
| `parse(payload)` | 平台消息体转内部标准格式 |
| `send(conversation_id, msg_type, content)` | 把回复发到平台，返回成功或错误 |

核心服务只认这三个方法。新增企业微信时写一个子类、在 `service.py` 的 `ADAPTERS` 注册表里挂一行，其余不动。这条是可验证的：`grep -r "feishu" core/` 只有一处平台名出现在注册表里。

## 标准消息格式

所有平台的消息进系统第一件事就是转成这个结构，后续代码只认它。

| 字段 | 说明 |
|---|---|
| `id` | 系统内部 ID，uuid |
| `platform` | `feishu` / `dingtalk` / `wecom` |
| `event_id` | 平台事件唯一标识，**幂等键** |
| `conversation` | `{id, name}`，会话 |
| `sender` | `{id, name}`，发送人 |
| `msg_type` | `text` / `file` / `todo` |
| `content` | 文本用 `{text}`，文件用 `{file_name, file_key}` |
| `reply_to` | 回复的目标消息 ID，普通消息为空 |
| `status` | 当前状态，见状态机 |
| `version` | 乐观锁版本号 |
| `created_at` / `updated_at` | 时间戳 |

校验不通过的消息不丢，标记为 `parse_failed` 入库，等人工复核。

## 幂等去重

平台 Webhook 会在超时或网络抖动时重复投递同一个事件，如果不拦，页面上会出现重复消息，用户还会重复回复。

实现方式：`messages` 表上 `event_id` 建 UNIQUE 约束，插入时靠数据库保证唯一。重复事件命中 `IntegrityError`，代码把它转成返回值而不是抛出去：

```python
try:
    conn.execute("INSERT INTO messages (...) VALUES (...)")
except sqlite3.IntegrityError:
    return False   # 已存在，丢弃
```

界面上的「投递重复事件」按钮就是拿最近一条消息的 `event_id` 再投一次，可以看到系统返回 `duplicate`，消息总数不变。这条能现场验证，不用只靠嘴说。

## 状态机

消息有 11 个状态，不是随便改的。`config.STATUS_FLOW` 定义合法流转，`state_machine.check()` 在每次变更前校验，非法跳转直接抛 `IllegalTransition`，接口返回 400。

为什么非要做这层：状态是比赛要看的「闭环」凭据。如果状态能随便写，后台改一下状态标签就"闭环"了，这个证明没有意义。现在任何一步都得真的发生了才能推进。

另外每个状态变更写一条 `traces` 记录（状态、时间、说明），页面上"状态流转记录"那块读的就是它，可以做审计。

并发控制用版本号做条件更新：`version` 每次变更 +1，UPDATE 语句带上 `WHERE id = ? AND version = ?`（读到的那个值）。影响行数为 0 就说明刚才有人先改过，本次直接失败并提示刷新。

这一层不是摆设。单进程里线程锁就够了，但 Docker 起两个副本时锁管不到另一个进程，只有这条 SQL 才真正挡得住并发写。

## 实时推送用 SSE 而不是 WebSocket

WebSocket 更主流，但这里选了 SSE，理由是很实际的：

- 这个场景是单向的——服务端推状态给浏览器，浏览器用普通 HTTP 提交操作，不需要双向长连接。
- Flask 起 WebSocket 要额外挂 gevent 或 flask-socketio，部署复杂度上去一截；SSE 用一个 `Response(generator)` 就够。
- 浏览器端 `EventSource` 自带断线重连，不用自己写心跳和重连逻辑。

代价是并发连接多了以后每个连接占一个工作线程。当前定位是单团队、几十人量级，够用。真要做到 50 以上并发稳定在线，换 WebSocket + 异步框架更合适，这个写在 `docs/需求分析文档.md` 的 NFR-05 里。

## 发送失败与重试

回复发不出去是最容易断闭环的一环。处理顺序：

1. 状态先进 `replying`
2. 调 `adapter.send()`
3. 失败按指数退避重试，0.5s 起、逐次翻倍、最多 5 次（对应 NFR-01）
4. 5 次全失败，状态转 `dead`，记录最后一次错误，提示人工补发

界面上勾选「注入一次发送失败」，前两次会故意失败、第三次成功，可以直接看到重试和状态变化。

## 安全

做到的部分：

- 入口要登录，会话空闲 30 分钟失效（`app.py` 里按 `last_active` 判断），未登录的接口请求返回 401。
- 平台凭证全部走环境变量，`config.py` 里没有硬编码密钥，`.gitignore` 排除了 `.env` 和 `data/`。
- 口令比对目前是配置项直接比较，不是查数据库。

没做的部分，如实写在这里：

- 没有密码哈希存储（配置里是明文演示账号）。
- 钉钉回调的签名校验留了方法位置，没写实现。
- 没有 HTTPS 配置，本地和演示环境是 HTTP。

## 已知取舍

| 现在的做法 | 为什么 | 什么情况下该换 |
|---|---|---|
| SQLite 单文件 | 零依赖，一条命令启动，演示方便 | 多实例部署时换 MySQL，只改 `store.py` |
| 单账号配置登录 | 定位单用户单团队，做用户表收益低 | 需要多人独立账号时加 users 表和密码哈希 |
| SSE | 单向推送够用，实现成本低 | 并发连接过 50 或需要双向时换 WebSocket |
| 模拟事件源 | 平台账号审批还没下来，不能卡着不开发 | 凭证到位后 `UMM_MODE=real` 走真实接口 |
| 无负载均衡 | 单机演示，加分项优先级低于闭环 | 决赛前有余力再补 Docker Compose 多实例 |
